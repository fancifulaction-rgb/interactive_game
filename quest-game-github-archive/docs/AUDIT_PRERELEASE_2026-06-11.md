# Аудит перед релизом — Quest Game (2026-06-11)

Полный предрелизный аудит кода: баги, проблемы стабильности, уязвимости. Версия приложения на момент аудита: **1.2.16**, ветка `main`.

Это **главный handoff-документ** для следующего агента. Промт для него — в конце (§11). Каждая находка имеет ID `IMP-*` (реестр — [IMPROVEMENTS_CATALOG.md](IMPROVEMENTS_CATALOG.md), раздел **M**).

## Методология

- 4 параллельных аудита: hot-path игрока + realtime, безопасность (RLS/Edge/секреты), админ/данные, build/CI/конфиг/зависимости.
- Критичные находки перепроверены вручную по коду.

**Легенда проверки:**
- ✅ **verified** — перечитан код лично, факт подтверждён на текущем `main`.
- 🔎 **reported** — найдено аудитом, не перепроверял построчно (но описание/фикс достоверны).

**Приоритеты:** **P0** — блокер релиза (безопасность/потеря данных/краш на нагрузке). **P1** — стабильность/UX под нагрузкой. **P2** — гигиена/техдолг.

## 1. P0 — Безопасность

### IMP-SEC-013 — anon SELECT утекает эталонный `answer` ✅
- **Файл:** `docs/sql-migrations/021_drop_legacy_rls_allow_all.sql:31-32`
- **Суть:** миграция 021 (после 011/018, которые ужесточали доступ) пересоздаёт `CREATE POLICY questions_anon_select ON questions FOR SELECT TO anon USING (true)`. Любой аноним читает таблицу `questions` целиком, включая колонку `answer` и скрытые вопросы (`is_hidden`). Это нивелирует `IMP-SEC-009` (view `questions_player`).
- **Также:** `players_anon_select USING(true)` (строки 58-59) — утечка ПДн участников.
- **Фикс:** не давать anon прямой SELECT на `questions`/`players`. Для игрока — только view `questions_player` (без `answer`, только видимые). Новая миграция `035_fix_anon_questions_rls.sql`: `DROP POLICY questions_anon_select`, выдать `SELECT` на view, ограничить `players` (или убрать anon select полностью, читать через RPC). Проверить, что клиент игрока уже ходит в `questions_player`/RPC, а не в `questions`.

### IMP-SEC-014 — утечка ответов через scoreboard/grading RPC ✅
- **Где:** RPC/функции выдачи ответов на табло/проверку (`get_scoreboard_answers`, `list_pending_answers`, `get_teams_pending_review`, `list_posthoc_answers`).
- **Суть:** функция отдаёт правильные ответы/чужие ответы без проверки роли (anon может вызвать).
- **Фикс:** migrate `038_secure_grading_scoreboard_rpc.sql` — `auth.role()` только `authenticated`/`service_role`, `REVOKE EXECUTE FROM anon`. Админка уже с Supabase-сессией (`hasSupabaseAdminSession`). Проверка: `security-smoke.mjs` SEC-014.

### IMP-SEC-015 — публичная загрузка в Storage ✅
- **Где:** политики Storage / `player-upload`.
- **Суть:** запись в бакеты доступна по anon-пути без team session / без whitelisting бакета.
- **Фикс:** migrate `039_secure_storage_upload.sql` — DROP public INSERT на все buckets; INSERT только `authenticated` для `question-media`/`quest-logos`; `avatars`/`answer-media` — клиент через Edge `player-upload` (team session). `storageUpload.ts`: player buckets → edge first; admin media → JWT сессии. Проверка: `security-smoke.mjs` SEC-015.

### IMP-SEC-016 — IDOR на удаление/редактирование чужих игр 🔎
- **Где:** `delete-game` Edge / RPC правки игр/вопросов.
- **Суть:** нет проверки, что текущий админ — владелец игры. Зная `game_id`, можно удалить/изменить чужую игру.
- **Фикс:** модель владения (`games.owner_id` или admin-session scope) + проверка во всех мутациях; `verify_jwt` + `requireAuthenticatedUser` уже есть на delete (`IMP-SEC-012`) — добавить именно ownership-чек.

### IMP-SEC-017 — `process_game_schedule` доступен anon ✅
- **Где:** RPC планировщика (`029_game_schedule.sql`).
- **Суть:** аноним может триггерить смену состояния игры по расписанию.
- **Фикс:** migrate `040_lock_process_game_schedule_grants.sql` — auth guard + `REVOKE EXECUTE FROM anon`. Админ-панель (`GameSchedulePanel`) вызывает под authenticated. Проверка: `security-smoke.mjs` SEC-017.

### IMP-SEC-018 — перехват сессии команды (`recover_team_session`) ✅
- **Суть:** восстановление сессии команды по слабому признаку (имя/код) позволяет угнать чужую команду и отправлять ответы за неё.
- **Фикс:** восстановление только с проверкой исходного session token или одноразового кода; rate-limit; не отдавать токен по угадываемым данным.

### IMP-SEC-019 — `join_token` не обязателен ✅
- **Где:** регистрация по ссылке (`032_game_join_token.sql`, `register_team`).
- **Суть:** регистрация работает и без валидного `join_token`, токен не enforced → обход уникальной ссылки/контроля доступа.
- **Фикс:** если у игры задан `join_token` — требовать его в `register_team`; иначе fail-closed.

### IMP-SEC-020 — Edge `generate-questions` без auth и rate-limit ✅
- **Файл:** `supabase/functions/generate-questions/index.ts`
- **Суть:** нет проверки админ-сессии и лимитов → любой может жечь токены LLM-провайдера (Qwen/DeepSeek) и деньги.
- **Фикс:** `verify_jwt`/admin-session чек + rate-limit (по IP/админу) + лимит размера запроса.

### IMP-SEC-021 — git-tracked `alternative-upload` 🔎
- **Файл:** `supabase/functions/alternative-upload/index.ts` (в индексе git).
- **Суть:** обходной незащищённый upload-путь.
- **Фикс:** удалить функцию и из `git`, и из любых deploy-скриптов; оставить только `player-upload`.

### IMP-SEC-022 — захардкоженные JWT-ключи в репозитории ✅
- **Файлы (git-tracked):** `debug_questions.js`, `test_with_data.mjs` и др. отладочные скрипты в корне.
- **Суть:** в коде зашиты ключи Supabase (anon/возможно service). Утечка ключей.
- **Фикс:** удалить файлы из git (и из истории, если ключ — service role: **ротация ключа обязательна**), вынести в `.env`/CI secrets, добавить в `.gitignore`. Прогнать `gstack-cso` секрет-скан.

### IMP-SEC-023 — обход админ-доступа через localStorage 🔎
- **Где:** клиентская проверка админ-сессии (контекст/guard).
- **Суть:** доступ к админ-UI определяется значением в localStorage без серверной валидации → подделка флага открывает панель (UI; реальные мутации всё равно должны падать на RLS, но утечка структуры/действий возможна).
- **Фикс:** проверять админ-сессию серверно (RPC `17_admin_session`) перед рендером действий; localStorage — только кэш, не источник правды.

### IMP-SEC-024 — лишние anon-grants и CORS `*` 🔎
- **Суть:** ряд RPC (`get_teams_pending_review`, `track_product_events` и т.п.) и Edge-функций имеют широкий grant `anon` / `Access-Control-Allow-Origin: *`.
- **Фикс:** ревизия всех `GRANT ... TO anon`; CORS — whitelist доменов прод/стейдж. Свести в `SECURITY.md`.

> Прод-применение ужесточённого RLS отслеживается как `IMP-SEC-008` (в коде done), приватные бакеты — `IMP-SEC-002` (proposed). Перед релизом — подтвердить, что на **проде** применены миграции 011/018/035 и закрыты anon-grants.

## 2. P0 — Корректность, hot-path и БД

### IMP-INF-011 — `013_realtime_game_state.sql` отсутствует в манифесте ✅
- **Файл:** `scripts/lib/migration-manifest.mjs` (нет в `ALL_MIGRATION_FILES`), файл существует: `docs/sql-migrations/013_realtime_game_state.sql`.
- **Суть:** коллизия номера 013 (в манифесте только `013_submit_auto_answer.sql`). На свежей БД не настраивается realtime-публикация `game_state` → табло/состояние не обновляются по Realtime.
- **Фикс:** переименовать realtime-миграцию в свободный номер (напр. `035_...`/`036_...`) или добавить явно в манифест, сохранив порядок применения.

### IMP-INF-012 — `006_storage_buckets.sql` и `007_fix_mojibake.sql` отсутствуют в манифесте ✅
- **Файл:** `scripts/lib/migration-manifest.mjs` (gap 005 → 008).
- **Суть:** на свежей БД не создаются storage-бакеты → загрузки падают; не применяется fix mojibake.
- **Фикс:** добавить `006_storage_buckets.sql` и `007_fix_mojibake.sql` в `ALL_MIGRATION_FILES` в правильном порядке; прогнать `db:verify-schema` и bootstrap «с нуля».

### IMP-LOG-023 — ответы игрока идут мимо `enqueueCritical` ✅
- **Файл:** `src/lib/submitAutoAnswer.ts:142-146`
- **Суть:** `enqueueSubmitAutoAnswer()` напрямую вызывает `submitAutoAnswerToServer()` — RPC `submit_auto_answer` уходит вне критической очереди. На 50+ телефонах одновременная отправка → всплеск параллельных запросов к Supabase, 429/таймауты (нарушение железного правила hot-path).
- **Фикс:** обернуть в `enqueueCritical` (как остальной hot-path игрока), убедиться что нет вложенных блокирующих `await` внутри critical.

### IMP-RT-007 — broadcast-шторм: `broadcastTeamsChanged` на каждый ответ ✅
- **Файл:** `src/lib/submitAutoAnswer.ts:119`
- **Суть:** `void broadcastTeamsChanged(req.game_id)` вызывается после **каждого** ответа любой команды → при массовой отправке штормит канал и провоцирует лавину перерисовок/REST у всех клиентов.
- **Фикс:** не слать `teams_changed` на каждый ответ; достаточно `broadcastScoreUpdate` (уже есть, по delta>0). Если нужен teams-refresh — throttle/debounce (напр. ≥3-5 c) и/или только для админ-табло.

### IMP-PERF-004 — Storage upload параллелит с REST в одной вкладке 🔎
- **Файл:** `src/lib/storageUpload.ts`
- **Суть:** загрузка медиа ответа может идти параллельно с критическим REST (нарушение правила «не параллелить REST + Storage»), хотя есть `cancelActiveStorageUpload`/`networkMutex` — проверить, что upload всегда вне окна critical и отменяется перед submit.
- **Фикс:** провести upload через ту же очередь/мьютекс; гарантировать порядок: отмена upload → submit ответа.

## 7. Рекомендации усиления (полный список)

Эти пункты не обязательно баги, но укрепляют продукт перед релизом. **Все они должны быть в работе у следующего агента** (часть уже как IMP):

1. **Закрыть anon-доступ к чувствительным данным** — только views/RPC, минимальные grants (`IMP-SEC-013/014/024`).
2. **Модель владения играми** (`owner_id`) и сквозная проверка во всех мутациях (`IMP-SEC-016`).
3. **Приватные бакеты + signed URL** для медиа (`IMP-SEC-002`).
4. **Отключить открытую саморегистрацию админов** до релиза, если не нужна (`IMP-SEC-005` — держать `rejected`/закрыто).
5. **Ротация и вынос секретов**, секрет-скан в CI (`IMP-SEC-022`, `gstack-cso`).
6. **Auth + rate-limit на всех Edge** (`generate-questions`, upload) (`IMP-SEC-020`).
7. **Нагрузочный тест 50–100 VU** с реальным сценарием и отчётом `LOAD_TEST_REPORT.md` (`IMP-INF-006`).
8. **Наблюдаемость**: Sentry/лог-агрегация ошибок фронта + алерты на 429/5xx Supabase (`IMP-INF-008` расширить) — **нет отдельного IMP, добавить `IMP-INF-017`**.
9. **CI-гейты**: lint + typecheck strict + `db:verify-schema` + bootstrap-с-нуля + `npm audit` + edge-verify (`IMP-INF-014/015/016`, `IMP-TD-011`).
10. **Security-заголовки nginx/CSP** (`IMP-INF-013`).
11. **Манифест миграций = источник правды**: bootstrap «с нуля» в CI обязателен (`IMP-INF-011/012`, `IMP-TD-011`).
12. **Единый realtime-канал на игру** (`IMP-RT-003`) — снижает число подписок при 100 командах.
13. **Фидбэк игроку при сбое ответа** (`IMP-LOG-027`) — критично для доверия на мероприятии.
14. **Документы:** обновить `SECURITY.md` (anon-grants, CORS, владение), при EU — `PRIVACY_GDPR.md` (`IMP-SEC-006`), `MANUAL_QA_CHECKLIST.md` под новые фиксы.
15. **Runbook on-call** на время мероприятия: что делать при 429/реалтайм-дауне (расширить `OPERATIONS.md`).

## 15. Деплой в прод — отдельная фаза (после ремонта)

Выполняется **отдельным агентом** после закрытия блоков A/B (минимум P0). Вводные владельца:

- **Хостинг:** платный сервер на **beget.com** + собственное доменное имя.
- **Доступ:** по SSH через MobaXterm; владелец готов выдать допуски деплой-агенту.
- **Владелец не технический** — агенту вести пошагово, простым языком, не предполагать действий «само собой».

Стек деплоя (Supabase-only): фронт — статическая SPA (`npm run build` → `dist/`), backend — облачный Supabase (тот же проект). Значит на сервере нужно: отдать `dist/` через web-сервер (nginx/Apache или статик-хостинг beget), задать `VITE_*` env при сборке, привязать домен + HTTPS, задеплоить Edge-функции (`supabase functions deploy`).

Деплой-агент должен в начале уточнить у владельца:
- Тип продукта beget: **VPS** (полный Linux: nginx/Node) или **виртуальный хостинг** (только статика через панель/FTP) — от этого зависит способ выкладки.
- Домен (имя), где управляются DNS-записи.
- Готов ли владелец выдать SSH-доступ деплой-агенту (или выполнять команды под диктовку).

Промт деплой-агента — передаётся владельцем отдельно (см. чат-handoff).
