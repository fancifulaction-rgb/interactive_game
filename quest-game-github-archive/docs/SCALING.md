# Масштабирование: 2–100 одновременных игроков

## Что уже заложено в коде

| Механизм | Зачем при 100 игроках |
|----------|------------------------|
| `requestQueue` (1 critical + 1 background **на вкладку**) | У каждого игрока свой браузер — очередь убирает «самоконкуренцию» внутри одной вкладки (ответ + insert + уведомления) |
| Регистрация → navigate сразу после INSERT | 100 игроков не ждут prefetch вопросов перед входом |
| Кэш `gamePlayCache` + state на табло | Табло не делает 2 тяжёлых запроса при открытии |
| Аватар **после** игры + jitter 0–15 с | 100 одновременных Storage POST размазываются по времени |
| Ответ с файлом через `uploadAnswerMediaQueued` | Медиа и insert не идут параллельно в одной вкладке |
| Retry Storage (3 попытки) | Кратковременные `ERR_CONNECTION_RESET` переживаются |
| Оптимистичный UI ответа + фоновый insert | Игрок не ждёт 50 с при сбое соседнего запроса |
| Realtime табло с задержкой 8 с | Меньше 100 WebSocket при одном открытии табло |

## Важно понимать

1. **Очередь — на клиенте.** 100 игроков = 100 независимых браузеров = 100 независимых соединений к Supabase. Это нормально для PostgREST; проблема была в **одном** браузере с 5–8 параллельными запросами на одно HTTP/2-соединение.

2. **Supabase (план и регион).** Проект в Frankfurt (`tvytsnnujaucoluoyvjq`). При 100 игроках проверьте в Dashboard: лимиты API, Storage bandwidth, Realtime connections. При пике «все закончили игру» — до 100 загрузок аватаров за ~15 с (jitter), не за 1 с.

3. **Почему «раньше с Minimax было быстрее».** Вероятные причины: меньше параллельных запросов в старой версии, не было `fetchWithRetry`/отладочных `debugLog` на каждый шаг, аватар не конкурировал с ответом. Следов Minimax в репозитории нет — отличия из накопленных правок и отладки.

4. **Рекомендации для продакшена 50–100 игроков**
   - Сжатие аватаров (`compressImage`) — уже есть.
   - Ограничить размер медиа в ответах — уже есть (5–50 МБ по типу).
   - Включить Replication для Realtime в Supabase Dashboard.
   - При частых 429/reset — апгрейд плана или CDN перед Storage.
   - Нагрузочный тест: `node scripts/measure-latency.mjs` + 10–20 браузеров вручную.

## Проверка

```bash
node scripts/e2e-game-flow.mjs
node scripts/measure-latency.mjs 26D4A6
```

Если Node &lt; 500 ms, а браузер тормозит — узкое место в параллельных запросах UI (очередь это смягчает).
